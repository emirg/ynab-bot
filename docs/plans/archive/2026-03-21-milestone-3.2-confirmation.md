# Plan: Confirmacion Opcional Pre-Registro (Milestone 3.2)

## Objective & Context
- **Status:** Completed
- **Goal:** Allow users to optionally preview an expense before it is created in YNAB, with inline-keyboard Confirmar/Cancelar buttons. Toggled via `/confirmacion on/off`, disabled by default.
- **Why:** Some users want a safety net to catch parsing mistakes before money is recorded. Default-off preserves the current zero-friction flow.

## Design Decisions

### Confirmation scope
The confirmation flow applies to **all three input paths** that create transactions: text, voice, and photo/receipt. Budget queries (`intent == 'query'`) are unaffected.

### Where to intercept
The cleanest interception point is **inside `ExpenseHandler`**, after `ExpenseService` returns a successful result but **before** the transaction is created in YNAB. This requires splitting the current `ExpenseService` pipeline into two phases:

1. **Parse phase** — validate user, parse message, enhance with learning, resolve account. Returns a fully-built `Expense` object (or error). No YNAB write.
2. **Commit phase** — takes the `Expense` and creates the transaction in YNAB, records learning, adds to recent_transactions.

When confirmation is enabled, `ExpenseHandler` calls the parse phase, shows the preview with inline buttons, and only calls the commit phase when the user taps "Confirmar". When confirmation is disabled, `ExpenseHandler` calls both phases in sequence (current behavior).

### Pending transaction storage
Use `context.user_data` (python-telegram-bot's per-user in-memory dict) to hold the pending `Expense` object and associated metadata (`user_config`, `budget_id`). This avoids database writes for ephemeral confirmation state. The pending data is keyed as `context.user_data["pending_expense"]`.

### Timeout / overwrite behavior
- No explicit timeout. If the user sends a new expense while one is pending, the old pending expense is silently replaced (overwritten in `user_data`).
- If the user taps "Cancelar", the pending expense is cleared.
- If the user taps a stale Confirmar/Cancelar button (after overwrite), it returns a "ya no es valida" message.

### Interaction with shared expenses
Shared expenses (`intent == 'shared_expense'`) go through the same confirmation flow. The preview message includes the split breakdown.

### Interaction with receipt images
Receipt expenses go through the same confirmation flow. The preview message is prefixed with the receipt header.

### Setting persistence
A new boolean column `confirm_before_create` on `user_configurations` (default `FALSE`). New DB migration v9.

### UI
- Preview message: reuses the existing `ExpenseResponseFormatter.format_success` output but with a header change ("Voy a registrar:" instead of "Gasto registrado exitosamente") and inline keyboard buttons.
- Inline keyboard: two buttons — `Confirmar` and `Cancelar`.
- Callback data pattern: `confirm_expense` and `cancel_expense` (routed in `bot.py` via `CallbackQueryHandler` with pattern `r"^(confirm|cancel)_expense"`).

## Constraints & Architecture
- All user-facing strings in Spanish.
- `confirm_before_create` defaults to `False` (disabled) — zero friction for existing users.
- Pending expense is stored in `context.user_data` (in-memory, per-user), NOT in the database. Lost on bot restart, which is acceptable — the user simply re-sends the expense.
- The `commit_expense` method must create a fresh `ynab_repository` from the factory at commit time (not reuse a stale one from parse time) to handle token refresh between parse and confirm.
- Milliunits invariant: amounts are x1000, expenses are negative. No change to existing logic.
- Per-user isolation: all reads/writes scoped to authenticated user via telegram_id.
