# Plan: Milestone 3.1 — /deshacer and /editar Commands

## Objective & Context
- **Status:** Completed
- **Harness Roadmap Marker:** 3.1
- **Goal:** Complete milestone 3.1 by implementing `/deshacer` (delete last transaction from YNAB) and `/editar` (correct amount, payee, category, or account of recent transactions). `/corregir` is absorbed into `/editar` — its category correction logic (fuzzy match + learning update) becomes part of `/editar categoria`, and the `/corregir` command is removed.
- **Why:** Users who make mistakes when logging expenses need the ability to fully undo a transaction or fix any field without using the YNAB app. Having separate `/corregir` and `/editar` commands for overlapping functionality is confusing — merging them into a single `/editar` command with optional index support provides a cleaner UX.

## Design Decisions

### Time Window
The roadmap specifies "ultimos 5 minutos o ultima transaccion del dia". Both `/deshacer` and `/editar` will enforce: the target transaction must have been created within the last 5 minutes, OR be the most recent transaction created today (based on `created_at` in `recent_transactions`).

### Transaction Index (optional first argument)
`/editar` without an index operates on the **last** transaction (index 0). An optional numeric first argument selects a different transaction by index (1-based, as shown by `/recent`):
- `/editar categoria Restaurantes` — edits the last transaction
- `/editar 3 categoria Restaurantes` — edits the 3rd most recent transaction

`/deshacer` always operates on the most recent transaction (index 0). No index argument.

### Scope of `/editar`
`/editar` supports modifying four fields:
1. **Monto** (amount): `/editar monto 30000`
2. **Comercio** (payee): `/editar comercio McDonald's`
3. **Categoria**: `/editar categoria Restaurantes` — fuzzy-matched against YNAB categories
4. **Cuenta** (account): `/editar cuenta Tarjeta de credito` — fuzzy-matched against YNAB accounts

Multiple fields can be combined: `/editar monto 30000 comercio McDonald's categoria Restaurantes`.

This avoids LLM parsing overhead for a structured correction command.

### Absorbing `/corregir` into `/editar`
`/corregir` currently handles category corrections with learning updates via `correct_recent_transaction()`. This logic is absorbed into `/editar categoria`:
- **Fuzzy matching**: Same `_find_category_id_by_name()` resolution.
- **Learning updates**: Same `record_user_correction()` call (decrement old category association, increment new).
- **YNAB update**: Same `update_transaction_category()` / `update_transaction()` call.
- **Index support**: `/editar` accepts an optional index (1-based), replacing `/corregir`'s required index.

What gets removed:
- `LearningHandler.handle_correction_command()` — handler method
- `ExpenseService.correct_recent_transaction()` — service method
- `CommandHandler("corregir", ...)` registration in `bot.py`
- `/corregir` entry in help text (`format_command_list()`)
- Help tip mentioning `/corregir` in `format_help_message()`
- Existing `/corregir` tests adapted to test `/editar categoria` instead

### Account editing
YNAB API accepts `account_id` in the PUT transaction body to move a transaction between accounts. The user types an account name which is fuzzy-matched against their YNAB accounts. A new `_find_account_id_by_name` method will be added to `ExpenseService`, following the same pattern as `_find_category_id_by_name` (exact -> case-insensitive -> partial match).

Note: `recent_transactions` does not store `account_id`, so the response will show the new account name but not the old one.

### Layer placement
Following existing patterns:
- **Repository layer**: Add `delete_transaction` and `update_transaction` to `YNABRepository` interface + `YNABApiRepository` implementation.
- **Service layer**: Add `undo_last_transaction()` and `edit_last_transaction()` to `ExpenseService`. Remove `correct_recent_transaction()`.
- **Handler layer**: Add handler methods in `LearningHandler`. Remove `handle_correction_command()`.
- **Formatter layer**: Add formatting methods to `LearningResponseFormatter`. Keep `format_correction_success` and `format_correction_error` (used by `/editar categoria`'s response) or replace with the new `format_edit_success`.
- **Bot registration**: Register `/deshacer` and `/editar` commands. Remove `/corregir` registration.

### YNAB API Details
- **Delete**: YNAB API uses `DELETE /budgets/{budget_id}/transactions/{transaction_id}`. Returns the deleted transaction with `deleted: true`.
- **Update**: YNAB API uses `PUT /budgets/{budget_id}/transactions/{transaction_id}` with a partial transaction body. Already used for category updates; extend to support `amount`, `payee_name`, `payee_id`, `category_id`, and `account_id` fields.

### Learning cleanup on undo
When a transaction is deleted via `/deshacer`, the payee-category learning count should be decremented (same logic as the "old category" side of a correction). This prevents phantom learning from deleted transactions.

### Learning updates on category edit
When the category is changed via `/editar categoria`, apply the same learning logic as the old `/corregir`: call `record_user_correction(telegram_id, payee, old_category_id, new_category_id, new_category_name)`. This decrements the old association and increments the new one.

### Keyword parsing order
The handler must parse keywords in a defined order to avoid ambiguity. Keywords are: `monto`, `comercio`, `categoria`, `cuenta`. Each keyword captures its value(s) until the next keyword or end of args. Example: `/editar monto 30000 categoria Restaurantes` parses as `{monto: "30000", categoria: "Restaurantes"}`.

If the first argument is numeric (and not preceded by a keyword), it is consumed as the transaction index.

### Group 2: Service Layer (depends on: Group 1)

#### [x] Step 5: Add `undo_last_transaction()` to ExpenseService
- **Files:** `src/application/services/expense_service.py`
- **Action:** New method `undo_last_transaction(self, telegram_user_id: int) -> Optional[Dict]`. Logic:
  1. Get user config, validate configured.
  2. Get most recent transaction from `self.learning_repository.get_recent_transactions(telegram_user_id, 1)`.
  3. Check it exists and has `ynab_transaction_id`.
  4. Validate time window: `created_at` within last 5 minutes, OR it's the most recent transaction created today (parse the `timestamp` field from the dict, compare against user's current time using `user_now(user_config.timezone)`).
  5. Call `ynab_repository.delete_transaction(budget_id, ynab_transaction_id)`.
  6. If successful, decrement learning via `self.learning_repository.decrement_learning(telegram_user_id, payee, category_id)`.
  7. Remove the transaction from `recent_transactions` via `self.learning_repository.delete_recent_transaction(telegram_user_id, ynab_transaction_id)`.
  8. Return dict with `payee`, `amount`, `category_name` on success. Return dict with `error` key on validation failure. Return None on unexpected failure.
- **Tests:** `tests/test_expense_service.py` — Test: successful undo, no recent transactions, transaction too old (outside 5-min window and not today's), missing ynab_transaction_id, YNAB delete fails, user not configured. Follow existing `correct_recent_transaction` test patterns.

#### [x] Step 6: Add `edit_last_transaction()` to ExpenseService
- **Files:** `src/application/services/expense_service.py`
- **Action:** New method `edit_last_transaction(self, telegram_user_id: int, transaction_index: int = 0, new_amount: Optional[Decimal] = None, new_payee: Optional[str] = None, new_category: Optional[str] = None, new_account: Optional[str] = None) -> Optional[Dict]`. Logic:
  1. Get user config, validate configured.
  2. Get recent transactions from `self.learning_repository.get_recent_transactions(telegram_user_id, max(transaction_index + 1, 20))`.
  3. Check `transaction_index` is within bounds; if not, return error dict.
  4. Select the transaction at `transaction_index`.
  5. Validate time window (same as undo).
  6. Create YNAB repository via factory: `ynab_repository = self.ynab_factory.get_repository(user_config)`.
  7. Build `fields` dict for YNAB update:
     - If `new_amount`: convert to milliunits (`int(new_amount * -1000)`) and add as `"amount"`.
     - If `new_payee`: add as `"payee_name"`. Also attempt payee matching via `_match_payee()` to set `"payee_id"`.
     - If `new_category`: load categories via `ynab_repository.get_categories(budget_id)`, call `_update_llm_parser_data()` to build lookup maps, then resolve via `_find_category_id_by_name(new_category, categories)`. If no match found, return error dict: `{"error": "No encontre una categoria que coincida con '<input>'."}`. Add resolved `category_id` to fields. Look up the resolved category name for the response.
     - If `new_account`: load accounts via `ynab_repository.get_accounts(budget_id)`, resolve via `_find_account_id_by_name(new_account, accounts)` (new method, see Step 6b). If no match found, return error dict: `{"error": "No encontre una cuenta que coincida con '<input>'."}`. Add resolved `account_id` to fields.
  8. Call `ynab_repository.update_transaction(budget_id, ynab_transaction_id, fields)`.
  9. Handle learning updates:
     - **Amount or payee edits**: No learning changes needed.
     - **Category edit**: Call `self.learning_repository.record_user_correction(telegram_user_id, payee, old_category_id, resolved_category_id, resolved_category_name)` to update learning. This absorbs the core logic from the old `correct_recent_transaction()`.
     - **Account edit**: No learning changes (accounts are not part of the learning system).
  10. Return dict with old/new values on success, including which fields changed.

## Constraints & Architecture
- **Milliunits**: When editing amount, convert user input to YNAB milliunits (x1000, negated for expenses). The `fields` dict sent to YNAB API must use milliunits.
- **Per-user isolation**: All operations scoped via `telegram_user_id`. YNAB repo created per-user via factory.
- **Time window**: Enforced in service layer, not handler. Service returns error dict if outside window.
- **UI language**: All user-facing strings in Spanish.
- **No DB migration needed**: `recent_transactions` table already has `ynab_transaction_id` (added in migration v6) and `created_at` timestamp. No schema changes required.
- **Reuse fuzzy matching**: Category resolution reuses the existing `_find_category_id_by_name()` with its 4-step matching (exact -> case-insensitive -> partial -> clean/no-emoji). Account resolution uses a new `_find_account_id_by_name()` with a simpler 3-step matching (exact -> case-insensitive -> partial).
- **Learning consistency**: Category changes via `/editar` must trigger the same learning updates as the old `/corregir` (via `record_user_correction`). Amount, payee, and account changes do NOT affect learning.
- **Backward compatibility**: `update_transaction_category` in the repository is kept for now (other code may use it). The new `update_transaction` is a superset.
